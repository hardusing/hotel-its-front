# ディープリンク URL 仕様

トップページ（`/`）および今後追加する LP が受け取るクエリパラメータの定義。
このドキュメントは仕様のみを定める。実装はまだ無い（現時点で読まれているのは `lang` だけ）。

---

## 0. 全体方針：不正値はエラーにせず既定値に戻す

**すべてのパラメータについて、値が解釈できない場合はそのパラメータだけを黙って捨て、既定値で動作する。**
エラー画面を出さない。警告も出さない。他のパラメータの解釈も止めない。

理由：

- **広告のリンクは壊れやすい。** 配信管理画面での手入力、代理店側でのテンプレート置換ミス、配信システムが付与するリダイレクタでの再エンコード、SNS やメーラーによる URL の途中切断（末尾が欠ける）、`&` が `&amp;` に変換される、といった経路で日常的に値が変質する。
- 壊れた `checkin` ひとつでランディングをエラー画面にすると、**広告費を払って連れてきた人をその場で失う**。パラメータは「あれば嬉しい初期値」であって、ページが成立するための必須条件ではない。
- 予約の正しさは URL ではなく後段が担保する。金額は `calculatePrice` が、在庫と最終的な予約可否はサーバー応答（`OUT_OF_STOCK` / `VALIDATION_ERROR`）が決める。URL の値を信用しなくても安全側に倒れる構造になっている。

この方針の帰結として、**URL は「ヒント」であり「状態の正」ではない**。復元できなかった項目は、利用者が画面上で入力し直せる状態（＝通常の初期状態）で提示する。

## 1. パラメータ一覧

### 1-1. 予約フローに影響するもの

画面の初期状態を変える。値の妥当性を検証したうえで反映する。

| 名前 | 型 | 例 | 既定値 | 不正値のときの扱い |
|---|---|---|---|---|
| `room` | 整数（客室 ID） | `room=3` | なし（モーダルを開かない） | 数値に解釈できない／該当 ID の客室が一覧に無い場合は無視。モーダルを開かず一覧のみ表示する。`room` が無効なら `checkin`/`checkout`/`guests`/`promo` も反映先が無いため併せて破棄する |
| `checkin` | 日付文字列 `YYYY-MM-DD` | `checkin=2026-09-12` | 未選択（`日付を選択してください`） | 書式不正・実在しない日付・過去日（`todayStr()` より前）は無視。`checkin` を捨てた場合は `checkout` も併せて捨てる（片側だけの日付は意味を持たないため） |
| `checkout` | 日付文字列 `YYYY-MM-DD` | `checkout=2026-09-14` | 未選択 | 書式不正・`checkin` 以前・`checkin` と同日は無視。この場合 `checkin` は残し、チェックアウトのみ未選択にする |
| `guests` | 整数（人数） | `guests=2` | `min(2, room.capacity)` | 数値でない／1 未満／`room.capacity` 超過は無視して既定値。※上限超過は「上限に丸める」のではなく既定値に戻す（丸めると意図しない人数で見積もりが出るため） |
| `promo` | 文字列（クーポンコード） | `promo=EARLY30` | 空（未適用） | 空文字・空白のみは無視。**存在しないコードでも URL 層では弾かない**。前後空白を除去し大文字化して適用処理に渡し、使えるかどうかは `calculatePrice` の判定に委ねる（URL 層とクーポン判定に二重の正解を置かないため） |
| `lang` | 列挙（`ja` \| `en`） | `lang=en` | `navigator.language` による自動判定 | `translations` に存在しないキーは無視して自動判定にフォールバック。**実装済み**（[index.js:63-70](../src/index.js#L63-L70)） |

補足：

- `room` は現時点ではモック（`src/mock/rooms.js`）の ID `1`〜`3` に対応する。将来 slug に移行する場合は `room` を文字列許容に拡張し、数値ならば ID、それ以外は slug として解決する。
- `promo` という名前を使う（`coupon` ではない）。内部の変数名 `appliedCoupon` とは別物として扱い、URL 上の名前は変えない。

### 1-2. 計測にしか使わないもの

**画面の表示・金額・予約可否を一切変えない。** 記録して後段へ引き渡すだけ。

| 名前 | 型 | 例 | 既定値 | 不正値のときの扱い |
|---|---|---|---|---|
| `utm_source` | 文字列 | `utm_source=google` | 空（未計測） | 検証しない。空文字は無し扱い。長すぎる値は先頭 255 文字で切って保持 |
| `utm_medium` | 文字列 | `utm_medium=cpc` | 空 | 同上 |
| `utm_campaign` | 文字列 | `utm_campaign=autumn2026` | 空 | 同上 |
| `utm_content` | 文字列 | `utm_content=banner_a` | 空 | 同上 |

扱いの原則：

- **初回流入時に sessionStorage へ退避する。** `updateUrlParam()` が `replaceState` で URL を書き換えるため（[index.js:40-45](../src/index.js#L40-L45)）、後段で URL を読み直す前提にしない。
- 退避済みの値がある場合、後から来た同名パラメータで**上書きしない**（同一セッション内の初回接触を保持する）。
- 予約送信時に payload へ添える。現在の `createReservation` の payload には計測項目が無いため、フィールド追加はサーバー側と合わせて決める。
- 値の中身は検証しない。検証すべき正解を持たないうえ、弾いた分だけ計測が欠ける方が損失が大きい。

## 2. 想定 URL の実例

### (1) キャンペーン流入
広告バナーから、対象客室とクーポンを指定して着地させる。日付は利用者に選ばせる。

```
https://example.com/?room=3&promo=EARLY30&utm_source=google&utm_medium=cpc&utm_campaign=autumn2026&utm_content=banner_a
```

スイート（ID:3）のモーダルが開き、`EARLY30` が適用された状態。日付は未選択なのでカレンダーから選ぶ。utm 4種は sessionStorage に退避され、予約時に送られる。

### (2) 日付指定の再訪
一度検討した人へのリマーケティング、あるいは自分でブックマークした URL。

```
https://example.com/?room=2&checkin=2026-09-12&checkout=2026-09-14&guests=2&utm_source=mail&utm_medium=email&utm_campaign=remarketing
```

ダブル（ID:2）が 2泊・2名で復元され、料金内訳まで出た状態で着地する。在庫が無ければ通常どおり満室として扱われる（URL の指定は在庫を上書きしない）。

### (3) SNS 共有
利用者が見ていた画面を共有する。クーポンや計測は含めない。

```
https://example.com/?room=1&lang=en&utm_source=x&utm_medium=social
```

シングル（ID:1）を英語表示で開く。共有リンクに `promo` を載せない方針とし、共有経由でクーポンが無制限に拡散する状態を作らない。

## 3. 計測パラメータが増えた場合の拡張方針

新しい計測パラメータ（`gclid`、`fbclid`、`utm_term`、代理店独自の ID など）は日常的に増える。そのたびにコードを直す作りにしない。

1. **許可リストを 1 箇所の定数に集約する。** 計測パラメータ名の配列を一つ定義し、収集処理はその配列だけを見る。追加は配列に 1 行足すだけで済ませ、収集ロジックには触れない。
2. **前方一致で `utm_*` をまとめて拾う。** `utm_` で始まるパラメータは列挙せず全件収集する。`utm_term` のような後発の標準項目が、コード変更なしで載る。
3. **未知のパラメータは黙って無視する。** 許可リストにも `utm_` にも該当しない値は捨てる。URL に何が付いていても壊れないことを保証する。
4. **計測用と予約用の名前空間を分ける。** 予約フローに影響するパラメータ（1-1）は明示的に列挙したものだけとし、それ以外はすべて計測または無視に倒す。新しい計測項目が誤って予約状態を動かす経路を作らない。
5. **保存形式は key-value のまま持つ。** 個別のフィールドに展開せず、収集した全パラメータをひとまとまりのオブジェクトとして sessionStorage に持ち、payload にもその形で添える。項目が増えてもストレージ側・送信側の構造を変えずに済む。
6. **上限を設ける。** 保持する件数（例：20 件）と 1 値あたりの長さ（例：255 文字）に上限を置く。URL は外部から任意に付与できるため、上限が無いとストレージと送信ペイロードが無制限に膨らむ。
